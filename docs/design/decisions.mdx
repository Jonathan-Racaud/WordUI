---
title: Design Decisions
description: Locked architecture decisions and the rationale behind them
---

This page records the **locked decisions** that define WordUI's architecture — the constraints
that every new feature and API surface must respect. For the full discussion and rejected
alternatives, see [`DESIGN.md`](https://github.com/vendinois/WordUI/blob/main/DESIGN.md)
in the repository root.

---

## 1. Modifiers act on the stack top (Rule B)

Always `Button("+"); OnClick(f);`, never `OnClick(f); Button();`.

**Why:** Because a closed container is left on the stack top, modifiers compose onto whole
containers for free: `...); Padding(8);`. Reversing the order would require modifiers to
look ahead in the stack, breaking the concatenative model.

---

## 2. Hybrid data passing

The stack form is primitive (`Str("x"); Label();`) and convenience overloads are sugar
(`Label("x")` ≡ `Str("x"); Label();`). Modifier parameters are always applicative
(`TextColor(.Red)`).

**Why:** The stack form preserves the concatenative flavor and is the API that word authors
target. Sugar overloads keep the common case concise. Applicative modifier parameters keep
the `modifier(value)` syntax readable (stack-based modifiers would be `value; modifier;`).

---

## 3. Delegate blocks for containers

User-facing containers use delegate blocks (`VStack(scope () => { … })`), implemented on top
of public paired primitives (`_VStack()` / `VStack_()`).

**Why:** The mixin-block alternative doesn't work: Beef evaluates mixin arguments
eagerly, before the body. Delegate blocks are the cleanest syntax that works. Keeping the
paired primitives public enables cross-function factoring when a single delegate block isn't
enough.

---

## 4. Rebuild-on-invalidate

`Build()` re-runs only after `Invalidate()`. Each run produces a fresh tree in a
`BumpAllocator` arena; the old tree is freed wholesale. State is plain Beef fields;
reactivity is `Invalidate()`. No diffing.

**Why:** Simplicity and correctness by construction. Diffing introduces a
whole class of bugs (stale references, missed updates). Whole-tree rebuild is the right
default for an experimental framework; memoization and `Model<T>` observables are earmarked
for optimization only if profiling proves them necessary.

**Repaint vs. rebuild.** Only app-data changes take the rebuild path. Visual-only changes
(interaction state, animation ticks) call `RequestRepaint()` (`mNeedsRepaint`) instead of
`Invalidate()` (`mDirty`), re-running only the paint pass on the existing tree. Interaction
happens far too often to rebuild for, and tearing down the arena mid-interaction was what
left a dangling `Widget*` and caused missed clicks. See decisions 7–9.

---

## 5. One widget class + three type-safe bags

`Widget` is `sealed`; the no-subclassing rule is compiler-enforced. Capabilities split
across three independent bags:

| Bag | Base class | Purpose |
|---|---|---|
| **Component** | `Component` (abstract) | Pipeline participants — `Measure`, `Draw*` hooks |
| **Property** | `Property` (abstract) | Pure data — `Describe` only, queried by other code |
| **Behavior** | `Behavior` (abstract) | Event handlers — `Describe` only, iterated by input dispatch |

Each bag has its own typed `Get*<T>()`, `Require*<T>(word)`, and `Attach*(T)` API.
`ReplaceComponent` (Component bag only) handles replacement semantics for pen blocks.

**Why:** Rebuild-on-invalidate makes widgets transient descriptions, not long-lived actors.
Behavior polymorphism moves to the three bag base classes (one level deep each). Capability
mixing is composition (bags handle combinatorial combinations that subclass trees can't).
The three-way split means each framework subsystem iterates exactly what it needs: the draw
loop iterates Components only; layout queries Components and Properties; input dispatch
iterates Behaviors. A single Component bag forced no-op virtual dispatches for data-only
and event-only types. Framework types and user types are peers in every bag; same virtual
hooks, no registration.

---

## 6. Direct SDL3 now; renderer/platform abstraction deferred

The framework uses SDL3 directly while the concatenative model is being validated — this is
purely about testing the thesis first and extracting the abstraction later. Drawing
flows through one concrete `Painter` module; `SDL_Event` is adapted to `InputEvent` at a
single boundary.

**Why:** The thesis under test is "can concatenative-style UI work for real apps?"; answered
entirely on the framework side (words, layout, composition), where the backend's identity is
irrelevant. A one-implementation abstraction is best **extracted** from working code later
than **designed** blind now. The localization discipline (single `Painter` class, single
event-adapter boundary) makes the eventual extraction a mechanical refactor rather than a
rewrite.

---

## 7. Interaction is resolved at draw, via field-level patches — not layers

A state body (`IfHover`, `IfPressed`, any `IfActive<T>`) always runs at build, but its
styling words record a field-level `StatePatch` rather than mutating base components. The
draw pass blends every active patch over the base, field by field, interpolating any fields
wrapped in `Transition`.

**Why:** The rejected alternative — **interaction layers** — cloned a whole property and
replaced it wholesale: boolean-only, whole-property, timeless. Two concurrently-active states
couldn't compose (one clobbered the other), and there was no place to carry animation. Patches
record only the touched fields, so concurrent states compose, and they carry a duration/curve
so animation falls out for free. Resolving at draw is also what keeps interaction off the
rebuild path (decision 4).

---

## 8. Persistent retained `Node` tree keyed by `StableKey`

Interaction state, animation clocks, and drag capture live in a retained `Node` tree owned by
`App`, outside the build arena, so they survive every rebuild. The tree mirrors the widget
hierarchy: each `Node` carries a `StableKey`, parent/child links, a generic
`Dictionary<int, Variant>` for capability-owned state (framework slots 1–99, user slots ≥ 100),
and per-state animation clocks that self-prune when settled. After each build,
`ReconcileTree()` matches the new Widget tree against the existing Node tree by `StableKey`:
matched Nodes are reused (state persists), new ones are created, and orphaned ones are
disposed. After reconciliation, stale state slots and clocks are pruned from reused Nodes:
any key not referenced by the current widget's `IInteractionState` properties (or the
framework-reserved set `StateSlots.FrameworkIds`) is removed, preventing unbounded growth.
Drag capture state is per-pointer-session and lives directly on `App`.

**Why:** An animation in flight (a hover fade at `t=0.1s`) must keep running when unrelated
app data changes and the tree is rebuilt. A `Widget*` can't be the key — the arena frees it
on rebuild, which is exactly the dangling pointer that caused missed/delayed clicks. A stable
key re-associates state with the same logical widget after a rebuild. Moving from a flat
`InteractionStore` to a tree of Nodes makes state local to the element that owns it, gives
it a natural lifecycle (parent/child → dispose), and lets capabilities define their own slots
without a central registry.

---

## 9. `StableKey` via a post-build path hash

`KeyAssign` walks the finished tree and sets each widget's key to
`hash(parentKey, Name, discriminator)`, where the discriminator is the author's `Key()` hint
when set (≥ 0) or the sibling ordinal otherwise. This retires the old positional `BuildIndex`.

**Why:** Deterministic and stable across rebuilds whenever the build structure is stable.
Folding the explicit `Key()` hint into the hash (rather than using it raw) keeps user keys and
auto keys in one collision-free space, so a list author can pin identity with `Key(index)`
without colliding with computed path hashes.

---

## 10. Block when idle, tick only when animating or dragging

The frame loop blocks in `SDL_WaitEvent` when nothing is happening (true ~0% idle CPU) and
switches to a ~16ms `SDL_WaitEventTimeout` frame clock only while a transition or drag is live
(`App.NeedsTick`).

**Why:** A UI framework has no reason to burn CPU when the user isn't doing anything, but
animation still needs a steady clock. Draw-time resolution (decision 7) makes both possible
from one loop: idle blocks, animation ticks, and neither requires a rebuild.

---

## 11. Explicit `Transition` words; drag as a render-time offset

Animation is opt-in per field via `Transition(ms, …)` — nothing moves unless asked. Drag
follows the pointer with a render-time offset and pointer capture, leaving layout untouched.

**Why:** Implicit CSS-style transitions were rejected as too magical for a word-based API;
explicit `Transition` composes with the word style and keeps control local. Drag-as-offset is
cheap (no relayout now) and leaves a clean seam for live reflow later without a rework. Event
handlers (`ClickHandler`, `DragHandler`) share one `List<Delegate>` ownership list, so adding
a handler kind needs no new lifetime plumbing.
