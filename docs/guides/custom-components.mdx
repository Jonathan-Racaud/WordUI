---
title: Custom Components
description: Tier 2 — subclass Component, Property, or Behavior and provide a get-or-create modifier word
---

When existing types don't cover your needs, create a new subclass of `Component`, `Property`,
or `Behavior` and a modifier word that get-or-creates it on the stack-top widget. This works
on **any widget**, in your own project, without touching the framework — the same extension
mechanism that powers the whole word vocabulary.

## Choosing the right bag

Before you write code, pick the right base class:

| If your type... | Subclass | Bag | Example |
|---|---|---|---|
| Participates in layout or rendering | `Component` | Component | `TextComponent`, `Interior`, `Boundary` |
| Holds pure data queried by other code | `Property` | Property | `TextStyleProperty`, `LayoutHint`, `PressState` |
| Handles an event (click, hover, focus) | `Behavior` | Behavior | `OnClickBehavior` |

The key question: does your type need `Measure`, `DrawBackground`, `DrawContent`, or
`DrawOverlay`? If yes, it's a `Component`. If it's pure data read by a `Component`
or the layout pass, it's a `Property`. If it's a delegate invoked by the input system,
it's a `Behavior`.

## The pattern (all three bags)

Every capability follows the same three-part pattern:

1. **A subclass** of `Component`, `Property`, or `Behavior` with the data and hooks you need
2. **A modifier word** that get-or-creates your type on the stack-top widget in the right bag
3. **`using static`** to bring your word into scope

### Property example: custom data

```beef
// A Property that holds accessibility metadata
public class AccessibilityProperty : Property
{
    public String Label;
    public bool IsFocusable;

    public override void Describe(String buf)
    {
        buf.Append(scope $" accessibility=\"{Label}\"");
    }
}

extension UI
{
    public static void Accessibility(StringView label)
    {
        let w = Top("Accessibility");
        var a = w.GetProperty<AccessibilityProperty>();
        if (a == null)
        {
            a = new:BuildAlloc AccessibilityProperty();
            w.AttachProperty(a);
        }
        a.Label = new:BuildAlloc String(label);
    }
}
```

### Behavior example: event handler

The framework's own `OnClick` is the canonical example:

```beef
public class OnClickBehavior : Behavior
{
    public ClickHandler Handler;

    public override void Describe(String buf)
    {
        buf.Append(" OnClick");
    }
}

extension UI
{
    public static void OnClick(ClickHandler h)
    {
        let w = Top("OnClick");
        var b = w.GetBehavior<OnClickBehavior>();
        if (b == null)
        {
            b = new:BuildAlloc OnClickBehavior();
            w.AttachBehavior(b);
        }
        RegisterHandler(h);
        b.Handler = h;
    }
}
```

### Component example: pipeline participant

A `Component` subclass that participates in the draw pipeline:

```beef
public class FilledRect : Component
{
    public Color FillColor = .White;

    public override void DrawBackground(Painter painter, Widget widget, Rect bounds)
    {
        painter.FillRect(bounds, FillColor);
    }

    public override void Describe(String buf)
    {
        buf.Append(scope $" fill={FillColor}");
    }
}

extension UI
{
    public static void FilledRect(Color c)
    {
        NewWidget("FilledRect");
        AttachComponent(new:BuildAlloc FilledRect() { FillColor = c });
    }
}
```

## The get-or-create rule

Always use `Get*<T>()` first and create only if null. This ensures:

- Multiple modifiers on the same widget share one instance
- No ordering dependency; modifiers compose in any order
- `Attach*`'s duplicate-detection doesn't fire

```beef
// Both work regardless of order
Label("X"); Accessibility("hello"); TextColor(.Red);
Label("X"); TextColor(.Red); Accessibility("hello");
```

## Replacement vs mutation

When you need to replace an existing instance entirely (like pen blocks do for `Interior`
and `Boundary`), use `ReplaceComponent` on the Component bag. Property and Behavior bags
don't have `Replace` — mutate the existing instance in place instead.

```beef
// Component: replace existing Interior
let interior = new:BuildAlloc Interior() { FillColor = .Red };
widget.ReplaceComponent(interior);

// Property: mutate existing instance
widget.RequireProperty<LayoutHint>("Center").CrossAlign = .Center;
```

## When to use Tier 2 vs Tier 1

| Tier 1 (factored word) | Tier 2 (new subclass) |
|---|---|
| Compose existing words | New data/behavior that existing types don't hold |
| Zero classes | One subclass + one modifier word |
| Applies a preset style/behavior | Adds a new capability to any widget |
| Example: `TitleLabel(text)` | Example: `OnClick(handler)`, `Accessibility("label")` |

If you find yourself wanting to attach data or behavior to a widget that no existing type
stores, you need Tier 2. If you're just composing existing words into a named sequence,
stay at Tier 1.
