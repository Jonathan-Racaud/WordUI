WordUI uses **rebuild-on-invalidate**: plain Beef fields are the persistent state, `Build()`
describes the UI as a function of that state, and `Invalidate()` triggers a fresh widget tree.
There is no `Model<T>`, no `Bind`, no observable system — state is plain fields, reactivity is
`Invalidate()`. This is intentionally simple; it's the right default for an experimental
framework and easy to debug.

## The core loop

```
State (Beef fields)
    │
    ▼
Build()  ──►  word sequence  ──►  widget tree (BumpAllocator arena)
    │                                    │
    │                                    ▼
    │                              Layout pass  ──►  Rects
    │                                    │
    │                                    ▼
    │                              Paint pass  ──►  Pixels on screen
    │
    ▼
User clicks, handler calls Invalidate()
    │
    └── back to top ──┘
```

## The canonical pattern

```beef
class CounterSDLApp : SDLApp
{
    int mCount;                              // ← persistent state

    protected override void Build()
    {
        VStack(scope () => {
            Label(scope:: $"Count: {mCount}"); // ← read state
            Button("+"); {
                TextColor(.White);
                IfPressed(scope () => {
                    Fill(.(120, 120, 120, 255));   // highlight while pressed
                });
                OnClick(new => Increment);
            }
        });
    }

    void Increment()
    {
        mCount++;       // ← mutate state
        Invalidate();   // ← trigger rebuild
    }
}
```

## Interaction state: IfPressed

Interaction state (press, hover, drag) is deliberately **kept off the rebuild path** — it
happens far too often to tear down the tree for. `IfPressed` provides press feedback without
a rebuild: its body always runs at build and *records* a style patch, and the draw pass
applies that patch only while the widget is pressed. Pressing calls `RequestRepaint()`, which
re-runs only the paint pass on the existing tree.

The interaction cycle:

1. User presses mouse-down on a button → `PressTracker` sets the pressed flag in the persistent `InteractionStore`, keyed by the widget's `StableKey`, and calls `RequestRepaint()`
2. Paint pass re-runs → `StyleResolve` sees the `PressState` patch as active → highlighted button is drawn (no rebuild, no layout)
3. User releases mouse → `PressTracker` clears the flag and fires the `OnClick` handler → the handler calls `Invalidate()`
4. Now the tree rebuilds — but because app data (`mCount`) changed, not because of the press

The press highlight never touches app state, so it never triggers a rebuild. Only the click's
effect (mutating `mCount`) does. See the [Interaction Pipeline](/concepts/interaction-pipeline)
for the store, patches, animation (`Transition`), and drag.

## What survives a rebuild

**Plain Beef fields on your App subclass survive.** Everything allocated via `new:BuildAlloc`
during `Build()` (widgets, components, properties, behaviors, lists, string copies) dies
when the arena is deleted on the next rebuild.

| Survives | Dies on rebuild |
|---|---|
| `int mCount` | Every `Widget` |
| `List<String> mItems` | Every `Component` |
| `String mName` | Every `Property` |
| Any field on your App class | Every `Behavior` |
| | `Children` lists |
| | Arena-copied strings (`new:BuildAlloc String(...)`) |

## Lists and collections

Collections stored as App fields are the standard pattern for dynamic lists:

```beef
class CounterSDLApp : SDLApp
{
    List<String> mItems = new .() ~ DeleteContainerAndItems!(_);

    public this()
    {
        mItems.Add(new String("alpha"));
        mItems.Add(new String("beta"));
        mItems.Add(new String("gamma"));
    }

    protected override void Build()
    {
        VStack(scope () => {
            for (let item in mItems)
            {
                Label(item); Key(@item.Index);
            }
        });
    }
}
```

The `Key(@item.Index)` gives each dynamic child a stable identity: `KeyAssign` folds it into
the child's `StableKey`, so per-widget interaction state (and later, scroll position) tracks
the right item across rebuilds even as the list changes.

## When to call Invalidate()

Call `Invalidate()` whenever state that affects the UI changes:

- After a click handler mutates a field ✅
- After adding/removing an item from a list ✅
- After a timer fires ✅

Do **not** call `Invalidate()` inside `Build()`; that would cause an infinite loop.

The framework batches invalidations: calling `Invalidate()` multiple times between frames
only triggers one rebuild.

## Avoiding stale closures

Beef delegate closures capture variables by reference. This is usually what you want:

```beef
// ✅ mCount is captured by reference — the handler reads the current value
Button("+"); OnClick(new () => { mCount++; Invalidate(); });
```

But be careful with loop variables:

```beef
// ❌ All handlers capture the same `item` reference — they all see the last item
for (let item in mItems)
{
    Button(item); OnClick(new () => { Select(item); });  // BUG!
}

// ✅ Copy to a local that won't change
for (let item in mItems)
{
    let captured = item;
    Button(captured); OnClick(new () => { Select(captured); });
}
```

## No observers (yet)

Observer-based granular updates (`Model<T>`, `Bind`) are earmarked for optimization only if
whole-tree rebuild proves too slow in real apps — to be measured, not assumed. The current
model is simple and easy to reason about; no point adding complexity before it's needed.
