## Prerequisites

- [Beef toolchain](https://www.beeflang.org/) (`BeefBuild` on your PATH; or use `build` from the project's devenv)
- SDL3 development libraries only when building the `WordUISDL` backend/example (installed via your system package manager or the project's Nix/devenv environment)
- The Raylib Beef binding when building `WordUIRaylib`; it is a separate backend dependency and is not required by the core `WordUI` project

## Build & run

```sh
# From the workspace root
build

# Run the counter demo
./build/Debug_Linux64/WordUI/WordUI
```

The counter demo opens an SDL3 window with a centered title label, `+`/`-` buttons in a
horizontal stack, and a dynamic count display. The `+` button animates its background on
hover (`IfHover` + `Transition`) and highlights instantly on press (`IfPressed`) — both
resolved at draw with no rebuild. Clicking a button mutates the count and calls
`Invalidate()`, which rebuilds the tree; the window otherwise idles at ~0% CPU, waking only
for input or a live animation.

## Diagnostics flags

The binary accepts test flags that verify stack-hygiene error handling:

```sh
./build/Debug_Linux64/WordUI/WordUI --test-mismatch    # Mismatched container close
./build/Debug_Linux64/WordUI/WordUI --test-unbalanced   # Missing close word
./build/Debug_Linux64/WordUI/WordUI --test-unclosed-pen # Unclosed pen block
./build/Debug_Linux64/WordUI/WordUI --test-leftover     # Unconsumed stack values
```

Each flag runs a negative-test app class that intentionally triggers a named error.

## Your first WordUI app

Create a new Beef project and add references to `WordUI` and `WordUISDL`. A minimal app
using the standalone SDL host:

```beef
using WordUI;
using static WordUI.UI;

class HelloApp : SDLApp
{
    int mCount = 0;

    public override void Build()
    {
        VStack(scope () => {
            Label(scope:: $"Count: {mCount}"); FontSize(32);
            Button("Increment"); OnClick(new => Increment);
        }); Padding(16);
    }

    void Increment()
    {
        mCount++;
        Invalidate();
    }
}
```

The key pattern, intentionally simple:

- **State lives in plain Beef fields** (`mCount`).
- **`Build()` describes the UI** as a function of that state: a sequence of words.
- **`Invalidate()` triggers a rebuild**: the old widget tree is freed wholesale and a fresh one is allocated in a bump arena.
- **Handlers close over state**: the `Increment` method reads and mutates `mCount`, then calls `Invalidate()` to reflect the change.

## Embedding in a Raylib application

The Raylib adapter uses an already-initialized Raylib window. The host owns the application
loop and drawing frame; WordUI polls Raylib input, updates its retained tree, and draws
through its `RaylibBackend`:

Add references to the `WordUI` and `WordUIRaylib` Beef projects.

```beef
using WordUI;
using RaylibBeef;
using static RaylibBeef.Raylib;

class GameUI : App
{
    protected override void Build()
    {
        VStack(scope () => {
            Label("Game UI"); FontSize(24);
            Button("Continue"); OnClick(new => ContinueGame);
        }); Padding(16);
    }

    void ContinueGame() { }
}

InitWindow(1024, 768, "My Game");
let app = scope GameUI();
let ui = scope RaylibBackend(app, GetFontDefault());
while (!WindowShouldClose())
{
    ui.Update();
    BeginDrawing();
    ClearBackground(RaylibBeef.Color(30, 30, 30, 255));
    ui.Draw();
    EndDrawing();
}
CloseWindow();
```

`RaylibBackend` does not initialize or close the window and does not unload the supplied
font. `Update()` forwards pointer, wheel, and key input, advances animations, and performs
pending build/layout work. Call `Draw()` inside Raylib's drawing frame. For applications
that draw every game frame, it is fine to call `Draw()` every iteration.

## Project structure

```
backends/
├── SDL/           # Optional SDL host, event loop, and painter project
└── Raylib/        # Optional host-driven Raylib painter project
src/
├── Core/          # Foundation: Widget (sealed, 3 bags), Component/Property/Behavior (base classes), UI (stack + core ops), App, IPainter, Layout, HitTest, InputEvent, KeyCode, Rect, Size, Color, Primitives
│                  #   + interaction pipeline: KeyAssign (StableKey), Node (retained tree), Interaction (IfActive/Transition), StyleResolve, Easing, InputDispatcher, ITracker, IInputHandler, PointerCapture
│                  #   + tick/animation: ITickable, AnimationState (per-Node eased-progress clocks)
├── Components/    # Pipeline participants: TextComponent, Interior, Boundary, StackLayout, Children, ClipRegion, ScrollView, RenderDragOffset
├── Properties/    # Pure data: TextStyleProperty, LayoutHint (+ CrossAlignment, SizingConstraints), PressState/HoverState (+ IInteractionState), StatePatch/InteractionStyle
├── Behaviors/     # Event handlers: OnClickBehavior (+ ClickHandler), OnDragBehavior (+ DragHandler), ScrollHandlerBehavior (+ ScrollHandler), KeyboardHandler (+ KeyHandler), FocusHandler
│                  #   + input handlers: PressHandler, HoverHandler, DragHandlerBehavior, ScrollHandlerBehavior, FocusHandler, KeyboardHandler
├── Widgets/       # Word definitions: Label, Button, Stack, Spacer, Scrollable
├── Modifiers/     # Modifier words: Padding, Spacing, TextColor, FontSize, Alignment, Sizing, Styling (pen blocks), Clip, Vertical/Horizontal
├── Diagnostics/   # Diagnostics words: PrintStack, DumpTree
└── Program.bf     # Entry point, counter demo, negative-test harnesses
```
