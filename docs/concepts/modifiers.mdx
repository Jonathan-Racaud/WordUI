title: Modifiers & Pen Blocks
description: How modifiers act on the stack top, the three-bag get-or-create pattern, and pen blocks for styling
---

Modifier words and pen blocks are how WordUI applies styling and layout on the widget stack.
The key insight is simple: modifiers always act on whatever widget sits at the stack top,
which means they compose onto containers for free — no plumbing, no look-ahead, no special
syntax for "this applies to the parent."

## Modifier words

Modifier words follow **Rule B**: they always act on the widget currently at the top of the
stack. They pop it, modify it, and push it back:

```
TextColor ( widget color -- widget )
FontSize  ( widget float -- widget )
Padding   ( widget float -- widget )
```

This means modifiers compose freely, including onto containers that were just closed:

```beef
VStack(scope () => {
    Label("A");
    Label("B");
}); Padding(8);     // Padding on the VStack
   TextColor(.Red); // Also on the VStack (but VStack has no TextStyleProperty → error)
```

Modifiers use `Require*<T>` to validate the stack top has the expected type in the right
bag. Applying `TextColor` to an `HStack` produces: `"HStack has no TextStyleProperty —
TextColor does not apply to it"`.

## Modifier ordering is meaningful

Modifiers execute left-to-right, top-to-bottom. Each one modifies the widget and leaves it on top:

```beef
Label("Hello");
FontSize(24);     // sets font size on TextStyleProperty
TextColor(.Red);  // sets color on TextStyleProperty
// Widget now has TextStyleProperty { FontSize=24, TextColor=Red }
```

Modifiers after a container close act on the container:

```beef
HStack(scope () => {
    Button("+");
    Button("-");
}); Spacing(4);    // ← acts on the HStack widget's StackLayout
   Padding(8);     // ← acts on the HStack widget
```

## Target bag per modifier

Different modifier words target different bags on the widget:

| Modifier | Target bag | Target type |
|---|---|---|
| `TextColor`, `FontSize` | Property | `TextStyleProperty` |
| `Center`, `AlignStart`, `AlignEnd`, `AlignStretch` | Property | `LayoutHint` |
| `Width`, `Height`, `FixedSize` | Property | `LayoutHint` |
| `Padding` | Widget field | `Widget.Padding` (universal) |
| `Spacing` | Component | `StackLayout` |
| `OnClick` | Behavior | `OnClickBehavior` |

The bag is an implementation detail most of the time — you write `TextColor(.Red)` and it
just works. But it matters when you author your own modifier words: you need to choose
whether the data lives in a `Component`, `Property`, or `Behavior`.

## Get-or-create pattern

Most modifier words follow a **get-or-create** pattern. The modifier checks whether the
widget already has the target type; if yes, it mutates it in place. If no, it creates one
and attaches it:

```beef
// Property example: Center() get-or-creates a LayoutHint
public static void Center()
{
    let w = Top("Center");
    var hint = w.GetProperty<LayoutHint>();
    if (hint == null)
    {
        hint = new:BuildAlloc LayoutHint();
        w.AttachProperty(hint);
    }
    hint.CrossAlign = .Center;
}

// Behavior example: OnClick get-or-creates an OnClickBehavior
public static void OnClick(ClickHandler h)
{
    let w = Top("OnClick");
    var b = w.GetBehavior<OnClickBehavior>();
    if (b == null)
    {
        b = new:BuildAlloc OnClickBehavior();
        w.AttachBehavior(b);
    }
    RegisterHandler(h);
    b.Handler = h;
}
```

This ensures a modifier works whether it's the first or Nth one on a widget; no ordering
dependency. The pattern is the same across all three bags.

## Interaction state modifiers (IfPressed, IfHover)

`IfPressed` and `IfHover` are **state modifiers**. Unlike an ordinary conditional, their body
**always runs** at build — but inside it, styling words don't mutate the base components.
They record a field-level **style patch** that the draw pass applies only while the state is
active:

```beef
Button("+"); {
    TextColor(.White);
    IfHover(scope () => {
        Transition(150, scope () => { Fill(.(90, 90, 90, 255)); });   // fades in on hover
    });
    IfPressed(scope () => {
        Fill(.(120, 120, 120, 255));   // instant while pressed
    });
    OnClick(new => { mCount++; Invalidate(); });
}
```

How it works: both are `IfActive<T>` specializations (`IfActive<PressState>`,
`IfActive<HoverState>`). `IfActive<T>` get-or-creates the state property `T` on the stack-top
widget, then runs the body with a fresh `StatePatch` as the recording target. Styling words
that fire inside record their field onto the patch instead of touching the base; the patch is
tagged with its gating state and stored on the widget's `InteractionStyle`. At draw,
`StyleResolve` asks the state `IsActiveFor(widget.StableKey)` (reading the persistent
`InteractionStore`) and blends the active patches over the base values, field by field.

This is why press and hover no longer rebuild the tree — they call `RequestRepaint()`, and
the changed look is resolved at draw. It's also why concurrent states **compose**: a
hover patch that sets `Fill` and a focus patch that sets `TextColor` both apply. Wrapping a
recorded field in `Transition(ms, …)` animates it via a clock in the store that survives
rebuilds.

`IfActive<T>` is the generic mechanism; any `Property` that implements `IInteractionState`
can power a state modifier. See the [Interaction Pipeline](/concepts/interaction-pipeline)
for the full model, animation, and drag.

## Pen blocks

Pen blocks are a **modifier sub-vocabulary** for styling. They open a "pen" on the stack that
collects properties, then apply them all at once when closed:

```beef
Button("Submit");
Background(scope () => {
    Fill(.Blue);
    Radius(6);
});
Border(scope () => {
    Stroke(.White);
    StrokeWidth(2);
    Radius(6);
});
```

### How pens work

A pen block uses the same paired-primitive pattern as containers, but the closing word
calls `ReplaceComponent` on the Component bag — it removes any existing component in the
same abstract family and attaches the new one:

1. `_Interior()` pushes a named marker, then an `Interior` pen onto the stack
2. Pen property words (`Fill`, `Radius`) modify the pen on top
3. `Interior_()` pops the pen, validates it, calls `ReplaceComponent` to attach it to the
   widget below, and pops the marker

The stack effect is:

```
_Interior   ( widget -- widget mark pen )
Fill        ( widget mark pen color -- widget mark pen )
Radius      ( widget mark pen float -- widget mark pen )
Interior_   ( widget mark pen -- widget )
```

Using `ReplaceComponent` (not `AttachComponent`) means you can re-focus a widget with a
new `Background { ... }` block and it replaces the old `Interior` instead of triggering
a duplicate-component error. This is the replacement-semantics pattern: pens replace;
ordinary modifier words mutate in place.

### Pen property words

| Word | Pen type | Sets |
|---|---|---|
| `Fill(Color)` | Interior | Background fill color |
| `Radius(float)` | Interior, Boundary | Corner radius |
| `Stroke(Color)` | Boundary | Border stroke color |
| `StrokeWidth(float)` | Boundary | Border stroke width |

### Delegate sugar

Like containers, pens have delegate-block sugar:

```beef
Background(scope () => { Fill(.Red); Radius(8); });
// equivalent to:
_Interior(); Fill(.Red); Radius(8); Interior_();
```
