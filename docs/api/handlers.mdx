title: Handlers
description: Event handler words — OnClick, OnDrag, OnScroll, OnKey, and Focusable, and their delegates
---

Event handler words attach behavior to widgets using the **get-or-create pattern** on the
Behavior bag. This is how WordUI does interactivity — not through widget subclasses, but
through `Behavior` objects that any word can attach to any widget.

## OnClick

```
( widget ClickHandler -- widget )
```

```beef
Button("+"); OnClick(new => Increment);
```

Attaches an `OnClickBehavior` to the stack-top widget's Behavior bag (creating one if absent)
and registers the handler. Makes any widget clickable; no `ClickableButton` class ever needs
to exist.

### ClickHandler delegate

```beef
public delegate void ClickHandler();
```

A parameterless delegate. The handler typically closes over app state:

```beef
class CounterSDLApp : SDLApp
{
    int mCount = 0;

    public override void Build()
    {
        VStack(scope () => {
            Label(scope:: $"Count: {mCount}");
            Button("+"); OnClick(new => Increment);
            Button("-"); OnClick(new => Decrement);
        });
    }

    void Increment() { mCount++; Invalidate(); }
    void Decrement() { mCount--; Invalidate(); }
}
```

### What happens on click

1. SDL mouse-up event arrives at `SDLApp`'s event loop
2. `PressHandler` (keyed by `StableKey`, not a `Widget*`) checks: were mouse-down and mouse-up on the same widget?
3. If yes, it walks the hit-test chain, finds each widget's `OnClickBehavior`, and fires its `Handler`
4. The handler runs user code (e.g. `mCount++`)
5. The handler calls `Invalidate()` to trigger a rebuild

The press *highlight* itself doesn't go through this path — it's an interaction state
resolved at draw (`IfPressed`), so pressing requests a repaint, not a rebuild. See the
[Interaction Pipeline](/concepts/interaction-pipeline).

### Handler lifetime

Handlers registered via `RegisterHandler` are framework-owned, stored per build and freed
on the next rebuild. Events only ever dispatch against the current tree, so a handler
cannot outlive what it references.

### The get-or-create pattern on the Behavior bag

```beef
public static void OnClick(ClickHandler h)
{
    let w = Top("OnClick");
    var b = w.GetBehavior<OnClickBehavior>();
    if (b == null)
    {
        b = new:BuildAlloc OnClickBehavior();
        w.AttachBehavior(b);
    }
    RegisterHandler(h);
    b.Handler = h;
}
```

`OnClickBehavior` is a `Behavior` subclass — it lives in the Behavior bag, not the
Component bag. It has no `Measure`, `Draw*`, or other pipeline hooks; the input system
iterates the Behavior bag during event dispatch. This is the standard pattern for any
new event handler you author.

## OnDrag

```
( widget DragHandler -- widget )
```

```beef
Button("drag me");
OnDrag(new (dx, dy) => { mX += dx; mY += dy; Invalidate(); });
```

Makes the stack-top widget draggable by attaching an `OnDragBehavior`. On press over the
widget, `DragHandlerBehavior` begins a **pointer capture** in the persistent store keyed by
`StableKey`; while captured, every motion event routes to this handler with the incremental
delta since the last move — even when the pointer leaves the widget's rect. Release ends the
capture.

The visual follows via a render-time offset applied in `SDLApp.DrawWidget` — no relayout, no
rebuild — so a lightweight drag (that doesn't reflow siblings) needn't call `Invalidate()`
at all. See the [Interaction Pipeline](/concepts/interaction-pipeline) for capture and the
reflow seam.

### DragHandler delegate

```beef
public delegate void DragHandler(float dx, float dy);
```

Receives the incremental pointer movement (`dx`, `dy`) for each motion event during the drag.

## OnScroll

```
( widget ScrollHandler -- widget )
```

```beef
Scrollable(scope () => { ... });
OnScroll(new (offset) => { mScrolledTo = offset; });
```

Attaches an `OnScrollBehavior` to the stack-top widget. When a wheel event scrolls the widget,
`ScrollHandlerBehavior` adjusts its persistent offset (clamped to the content extent) and then invokes
this handler with the new offset. Unlike `OnDrag`, a wheel is a discrete impulse with no
capture — so `OnScroll` is a plain event consumer, not a gesture. The scroll itself (offset
storage + clipped translation) happens whether or not a handler is attached; `OnScroll` is for
*reacting* to it. See [Scrollable](/api/widgets#scrollable).

### ScrollHandler delegate

```beef
public delegate void ScrollHandler(float offset);
```

Receives the widget's new clamped scroll offset in pixels.

## OnKey

```
( widget KeyHandler -- widget )
```

```beef
TextField(); Focusable();
OnKey(new (keycode, modifiers) => { HandleKey(keycode, modifiers); });
```

Attaches a `KeyboardHandler` to the stack-top widget's Behavior bag. The handler fires
when a key is pressed **and** the widget holds focus (checked via
`App.FocusedKey == owner.StableKey`). Pair with `Focusable()` to make the widget
focusable; focus is managed independently by `FocusHandler`.

### KeyHandler delegate

```beef
public delegate void KeyHandler(int keycode, int modifiers);
```

- `keycode` — SDL keycode (platform-independent virtual key)
- `modifiers` — bitmask of SDL keymods (Shift, Ctrl, Alt, etc.)

## Focusable

```
( widget -- widget )
```

```beef
TextField(); Focusable(); OnKey(new (k, m) => { ... });
```

Attaches a `FocusHandler` to the stack-top widget's Behavior bag. On mouse-down over the
widget, `FocusHandler` sets `App.FocusedKey` to the widget's `StableKey`, writes
`StateSlots.Focus` (slot 5) to the retained Node, and requests a repaint (no rebuild).
The previously-focused widget has its focus cleared. Keyboard events are then routed by
`InputDispatcher` to the focused widget's `KeyboardHandler`.

Use `Focusable()` + `OnKey()` together for a keyboard-interactive widget; `Focusable()`
alone is enough if you just need focus tracking (e.g. for `IfFocused` styling).

## Authoring a new behavior

The pattern is the same for any event-driven capability (`OnClick` and `OnDrag` both follow
it):

1. Subclass `Behavior` with your delegate field
2. Write a modifier word that get-or-creates it on the Behavior bag
3. Register the delegate with `RegisterHandler` so the framework owns and frees it

```beef
public delegate void DoubleClickHandler();

public class OnDoubleClickBehavior : Behavior
{
    public DoubleClickHandler Handler;
}

extension UI
{
    public static void OnDoubleClick(DoubleClickHandler h)
    {
        let w = Top("OnDoubleClick");
        var b = w.GetBehavior<OnDoubleClickBehavior>();
        if (b == null)
        {
            b = new:BuildAlloc OnDoubleClickBehavior();
            w.AttachBehavior(b);
        }
        RegisterHandler(h);
        b.Handler = h;
    }
}
```

Note that *hover* is **not** a behavior — it's an interaction state resolved at draw
(`IfHover`). Reach for a `Behavior` when you need to fire user code on an event; reach for an
`IInteractionState` when you need state-dependent *styling*. See the
[Interaction Pipeline](/concepts/interaction-pipeline).
